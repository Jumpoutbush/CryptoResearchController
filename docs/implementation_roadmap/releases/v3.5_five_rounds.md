# v3.5 · 开发轮次 R11：多候选研究树的数据契约及冻结条件

> **执行状态：待开发（计划文件）**。本文是交给 Codex 的实施规格，并非已完成的功能说明。
> **基准：** `Jumpoutbush/CryptoResearchController@67618536ecd172b2fad24843daf291489e226c2e`；执行前以本机较新、已提交的源代码为准。
> **轮次类型：** 软件开发轮次；不得消耗任何个人科研项目的研究预算。

## 1. 本轮唯一目标

在一个冻结研究目标下登记少量相互竞争的候选构造和可证伪命题，保留分支的前提、关系、证据和否决边界；不能越过既有固定命题接口。

**现有基础：** `problem import/attempt start` 保存不可变问题版本，`engine/discovery_scheduler` 只允许单活动尝试；既有 `research_focus` 已锚定路线。

**进入条件：** v3.4 已能识别问题、证据和候选来源的版本。

## 2. 设计裁决与数据流

### 11.1 候选不是正式结论

候选节点状态 `PROPOSED/SCREENING/READY_FOR_ATTEMPT/ACTIVE/REFUTED/COVERED/RETIRED/CONDITIONAL`，不得提供 `PROVED` 作为模型可直接写入的状态。每个候选固定 `goal_anchor_id`、`problem_id` 或待核验草案、清楚的非平凡创新假设、最邻近工作、必备证明义务、否决判据和预估上下文成本。

### 11.2 树与依赖

父子关系代表“在某假设改变下产生新候选”，必要假设变更必须生成新的候选版本，不覆盖父节点；不同候选共享的引理通过 v3.4 知识图谱引用，未经独立核验的共享边保持候选状态。

## 3. 修改范围（新增文件均为规划路径）

- 新建 `candidate_search/model.py`、`candidate_search/catalog.py`、`candidate_search/validate.py`。
- 存储建议：`state/candidates/<project_id>/catalog.json` + 追加事件；可读的人类摘要位于 `projects/<id>/research/CANDIDATES.md`（可选）。
- 新建 `tests/test_candidate_contract.py`。
- 新增 `candidate list/propose/show` 命令（具体解析在本轮实施后公布）。

## 4. Codex 必须完成的实现步骤

1. 规定唯一键 `project_id + anchor_id + candidate_id + revision`，对同标题项目不合并。
2. 模型提交候选必须同时给出可证伪命题和最接近论文的待核查点，未检索全文时标记 `NOVELTY_PENDING`。
3. 验证“核心目标未改变”，新敌手模型/信任设置属于新修订并需要独立裁决。
4. 每一版本只能新增历史，禁止原地覆盖已经被否决的分支。
5. 添加最多 3 个 `SCREENING/READY/ACTIVE` 活跃候选的配置限制，超限拒绝或要求先退役。
6. 候选创建不自动修改 `STATE.next_task`、不导入固定问题、不触发模型调用。

## 5. 输入、输出与接口约定

示意候选卡：

```json
{
  "id": "C-0001",
  "revision": 1,
  "goal_anchor_id": "真实研究锚点",
  "problem_proposal_file": "research/candidates/C-0001/problem.json",
  "hypothesis": "可被明确反驳的候选声明",
  "closest_prior_work": ["核查过的来源 ID 或待核查占位"],
  "falsification_gate": "具体最小反例或覆盖判据",
  "status": "PROPOSED",
  "evidence_refs": []
}
```

路径和 ID 示例不允许绕过项目边界校验。


## 6. 必做的离线自动测试

- 创建同名不同假设的候选成功且 ID 不同。
- 同一候选原地改变敌手模型被拒绝；显式修订保留旧版本。
- 4 个同时活跃候选时拒绝新激活，已否决候选不占用活跃名额。
- 缺少否决判据/没有与冻结目标的关联时无法进入 `READY_FOR_ATTEMPT`。
- 错误编号、跨项目问题引用、循环分支关系被拒绝。

## 7. 本轮验收标准

- 同时登记 3 个候选，产生稳定、可审计的树结构，未调用模型。
- 原有 `attempt` 数量、权威主张状态及路线预算不变。
- 候选“未审/已否决/待证”含义在 CLI 中明确展示。

## 8. 停止、回滚及禁止事项

禁止从候选注册中直接宣布科研成功，也不允许把修订当作新路线逃避已有预算。

## 9. Codex 交付回执

- 填写修改文件列表、设计偏差及理由、`git diff --stat`。
- 提供专项测试与全套回归测试的真实命令、退出码、通过/失败数量。
- 输出一项**独立可复核**的正常路径证据和一项故障注入证据（测试文件/夹具/日志均可）。
- 报告是否改变既有科研项目的 `GOAL.md`、`STATE.json`、预算账本、门禁或任何证明结论；正常答案必须为“均未改变”。
- 使用英文、范围明确的 Git 提交说明；用户未授权时不要推送远端。

# v3.5 · 开发轮次 R12：单写者、多候选的有界研究调度

> **执行状态：待开发（计划文件）**。本文是交给 Codex 的实施规格，并非已完成的功能说明。
> **基准：** `Jumpoutbush/CryptoResearchController@67618536ecd172b2fad24843daf291489e226c2e`；执行前以本机较新、已提交的源代码为准。
> **轮次类型：** 软件开发轮次；不得消耗任何个人科研项目的研究预算。

## 1. 本轮唯一目标

让控制器在最多三个候选间按证伪价值选择下一项工作，复用 `run/attempt` 调用和原路线预算；调度器可以建议切换，但不创建并行写代理。

**现有基础：** `route_budget.total_budget/needs_review` 管理共享科研路线预算；`engine/discovery_scheduler` 还有固定问题尝试预算和唯一 active_attempt。

**进入条件：** R11 模型冻结与候选版本化完成。

## 2. 设计裁决与数据流

### 12.1 两层预算不重复计数

第 1 层：所有候选共用原路线 `effective_rounds`，只由既有 `runner.py` 更新。第 2 层：活动固定问题仍消耗其原有 attempt 预算。新候选调度器只记录选择建议、占用原因、选中轮次的映射，不再维护与前两者竞争的科研有效轮数。

### 12.2 评分只用于选任务

默认优先级：决定性反例可检验性 > 已知文献覆盖概率 > 安全/正确性主障碍 > 可直接推进冻结目标的程度 > 估计成本。评分必须附事实来源，绝不根据模型“感觉有前景”自动大幅转预算。若固定问题尝试仍活动，禁止自动关掉它；只可提出等当前检查点结束后切换的建议。

## 3. 修改范围（新增文件均为规划路径）

- 新建 `candidate_search/scheduler.py`、`candidate_search/cost_accounting.py`。
- 增加可选 `candidate select/plan/status` CLI；选择候选时仍按旧 `problem import/attempt start` 的明确要求执行。
- 新建 `tests/test_candidate_budget.py`、`tests/test_candidate_scheduler.py`。

## 4. Codex 必须完成的实现步骤

1. 选择前检查 `goal_anchor`、当前 route epoch、`last_processed_run` 与现有 active attempt。
2. 若固定尝试活动，只输出 `DEFERRED_UNTIL_ATTEMPT_CLOSE`，不创建第二个 attempt。
3. `candidate plan --dry-run` 显示各候选的证据、最小证伪动作、已消耗路线轮次和剩余预算，不写账本。
4. `candidate select` 只生成建议/待审草案；需要操作员显式确认固定问题 ID 和 `attempt start`；复评延期仍由原预算系统判断。
5. 发生预算耗尽、STOP、路线 pending_review 时禁止新候选执行，调用原路线复评流程。
6. 选中候选与每个实际 research run ID 一一记录，失败调用及监督费用分别归账。

## 5. 输入、输出与接口约定

候选选择可以引用一个建议评分，但不允许把分数写入科研证明状态。模拟输出：

```json
{
  "next_candidate": "C-0002",
  "required_action": "REVIEW_PROBLEM_BEFORE_ATTEMPT_START",
  "route_effective_rounds": 4,
  "route_budget_source": "state/routes/<project>.json",
  "candidate_evidence": ["真实证据引用"],
  "budget_extension_requested": false
}
```


## 6. 必做的离线自动测试

- 三个候选轮流评估后，路线有效轮次仍来自一个权威账本。
- 修改 candidate ID 或重新创建同假设候选不能重置原路线预算。
- 活动尝试未关闭不能切换固定问题版本。
- 未经人工命题核对不得自动导入 PROBLEM_PROPOSAL。
- 预算耗尽时选择建议被挂起，内置 route review 正常触发。
- 同时两个调度进程最多一个取得写许可。

## 7. 本轮验收标准

- 能在三个候选间展示证伪排序、具体决定性任务及真实剩余预算。
- 与 `research.cmd attempt status` 的活动状态完全一致。
- 无双重记账、无并行项目写入。

## 8. 停止、回滚及禁止事项

不建议本轮引入基于模型自评的强化学习式优先级调整；v4.0 的基准评价完成前维持保守规则。

## 9. Codex 交付回执

- 填写修改文件列表、设计偏差及理由、`git diff --stat`。
- 提供专项测试与全套回归测试的真实命令、退出码、通过/失败数量。
- 输出一项**独立可复核**的正常路径证据和一项故障注入证据（测试文件/夹具/日志均可）。
- 报告是否改变既有科研项目的 `GOAL.md`、`STATE.json`、预算账本、门禁或任何证明结论；正常答案必须为“均未改变”。
- 使用英文、范围明确的 Git 提交说明；用户未授权时不要推送远端。

# v3.5 · 开发轮次 R13：精确数学核验与形式证明适配器

> **执行状态：待开发（计划文件）**。本文是交给 Codex 的实施规格，并非已完成的功能说明。
> **基准：** `Jumpoutbush/CryptoResearchController@67618536ecd172b2fad24843daf291489e226c2e`；执行前以本机较新、已提交的源代码为准。
> **轮次类型：** 软件开发轮次；不得消耗任何个人科研项目的研究预算。

## 1. 本轮唯一目标

将已有整数反例、Lean 形式化及符号检验接口封装为**可选择的核验适配器**，明确各自能验证的声明范围与条件，避免“编译通过即论文定理成立”。

**现有基础：** 现有 `engine/falsification.py` 已有受限整数谓词反例；`engine/formal_verifier.py`、`verification_engine.py` 有 Lean/数学检查接口；主张图保存审查状态。

**进入条件：** R11—R12 完成，且 existing verify 相关回归通过。

## 2. 设计裁决与数据流

### 13.1 明确验证等级

统一回执状态：`EXECUTED/COUNTEREXAMPLE_FOUND/NO_COUNTEREXAMPLE_WITHIN_BOUND/TOOL_PASSED_AUDIT_PENDING/UNSUPPORTED/FAILED`。对整数搜索找不到反例，绝不标记全称命题已证。对 Lean 工具的输出，只记录源码、工具链、依赖、公理/声明名摘要；完整自然语言命题对应由独立审查者完成。

### 13.2 适配对象

优先考虑 NTRU 多项式恒等式、模算术关系、简单协议不变量和固定形式声明。复杂模拟安全游戏与分布安全界需要独立密码学审查，不能伪装成可自动判定的整数谓词。

## 3. 修改范围（新增文件均为规划路径）

- 新建 `candidate_search/verifiers/interface.py`、`integer_adapter.py`、`lean_adapter.py`。
- 可选 `symbolic_adapter.py` 仅包装现有确切接口，不应为新特性引入不受控 `eval`。
- 新建 `tests/test_verifier_adapters.py`，正例/伪例/错误绑定夹具。
- 回执写 `state/candidates/<id>/verification/`，指向权威 claim/prob 版本。

## 4. Codex 必须完成的实现步骤

1. 核对现有 verifier 函数参数和有效输入范围，尽量薄适配，不重写其安全校验。
2. 每条验证请求绑定 claim revision、problem SHA、候选修订及输入证据 SHA，防止旧结果重用。
3. 对整数反例输出具体见证，保存可由同一谓词验证器再次确认的机器证书。
4. 对 Lean 输出固定 toolchain、源码及目标 declaration 的哈希，区分工具执行与自然语义审查。
5. 检测 `sorry/admit` 等不允许占位，同时审查目标声明是否被弱化的风险。
6. 所有 `verify` 结果只通过原 `claim_graph` 审查流程影响正式证明状态。

## 5. 输入、输出与接口约定

建议共用接口：

```python
verify(request: VerificationRequest) -> VerificationReceipt
```

`VerificationReceipt` 必须包含 `claim_binding, source_hashes, adapter_id, tool_version, result_status, evidence_files, reproduction_command, limitations`。


## 6. 必做的离线自动测试

- 以一个错误多项式恒等式构造精确反例并成功复查证书。
- 将真命题搜索限制设为很小范围，输出 `NO_COUNTEREXAMPLE_WITHIN_BOUND` 而非 PROVED。
- Lean 声明 `True` 可编译却与目标安全命题不一致，必须显示人工语义审查待完成。
- 工具缺失、超时、SHA 不匹配或未知适配器返回 `UNSUPPORTED/FAILED`。
- 旧 claim 已修订后，先前的验证回执不能再次应用。

## 7. 本轮验收标准

- 至少一个精确反例和一个可重放的形式工具回执（Lean 不可用则给出明确 `UNAVAILABLE` 模拟记录）。
- 所有主张审查等级与原有 `claim_graph` 规则完全一致。
- 不增加不可信代码执行入口。

## 8. 停止、回滚及禁止事项

不能把模型生成的 Python 试验、统计观测或单次模拟器输出称为密码学证明；必须明确验证的是哪一层断言。

## 9. Codex 交付回执

- 填写修改文件列表、设计偏差及理由、`git diff --stat`。
- 提供专项测试与全套回归测试的真实命令、退出码、通过/失败数量。
- 输出一项**独立可复核**的正常路径证据和一项故障注入证据（测试文件/夹具/日志均可）。
- 报告是否改变既有科研项目的 `GOAL.md`、`STATE.json`、预算账本、门禁或任何证明结论；正常答案必须为“均未改变”。

# v3.5 · 开发轮次 R14：密码协议安全模型与模拟归约独立审查

> **执行状态：待开发（计划文件）**。本文是交给 Codex 的实施规格，并非已完成的功能说明。
> **基准：** `Jumpoutbush/CryptoResearchController@67618536ecd172b2fad24843daf291489e226c2e`；执行前以本机较新、已提交的源代码为准。
> **轮次类型：** 软件开发轮次；不得消耗任何个人科研项目的研究预算。

## 1. 本轮唯一目标

建立专门的协议级审查清单和强制人工独立审查接口，核对敌手腐化、泄漏、掉线、中止、模拟器与混合实验，而不宣称系统能自动证明任意密码协议安全性。

**现有基础：** `research/THREAT_MODEL.md`、`PROOF_OBLIGATIONS`、`research_quality` 的安全归约/证据回执、`claim review` 和 G0—G8 已提供理论门禁。

**进入条件：** R13 的验证回执等级及审查边界已经稳定。

## 2. 设计裁决与数据流

### 14.1 协议义务卡

每条安全声明保留 `security_game, parties, corruption_model, leakage_function, setup_assumptions, abort_behavior, simulator_interface, reduction_loss, composition_scope, dependencies`。如果本文原论文没有确切模型或界，必须标 `NEEDS_SOURCE`。

### 14.2 独立对抗性审查

审查代理尝试提出**固定假设下可验证的攻击执行**或识别归约缺失步骤。例如：恶意安全承诺不能自动保证查询结果来自认证数据库；选择性中止泄露需要明确定义；跨轮关联性不能由单轮匿名性直接推出。审查意见必须附上受影响的游戏与证明步骤；模型输出仅为 `REVIEW_FINDING`。

### 14.3 标准框架对比

必须与通用恶意安全多方计算、认证私有信息检索、通用零知识证明组合形成明确的假设/功能/成本差异表；只有有真实新增性质或非平凡复杂度界时，才进入构造推进。

## 3. 修改范围（新增文件均为规划路径）

- 新建 `candidate_search/security_model.py`、`candidate_search/security_review.py`。
- 新建 `tests/test_security_review.py`，恶意腐化、选择性中止、模拟器缺少输入等失败夹具。
- 添加 `templates/project/research/SECURITY_OBLIGATION_TEMPLATE.json`（模板仅供初始化使用）。
- 兼容原 `claim review proof_and_statement`、`claim review novelty` 接口。

## 4. Codex 必须完成的实现步骤

1. 设计字段校验，避免未列举泄漏函数就使用“完全隐私”等含混结论。
2. 每次审查报告绑定固定问题版本、真实候选版本、原论文位置与待审查证明路径。
3. 若模型检测到已知直接组合，标记 `POTENTIALLY_COVERED` 并要求原文定理级比较，不自动把候选设为已覆盖。
4. 通过三类最小反例：腐化阈值超出、选择性拒绝位泄露、模拟器无法重现公开输出。
5. 为安全归约损失的参数、位宽、轮数与失败事件建立显式表格（数学变量如需出现应在正式报告使用块级公式）。
6. 将独立审核证据写入候选审查报告，真正的 claim 状态只经原审核接口变动。

## 5. 输入、输出与接口约定

拟定 `security_review.json` 主要字段：

```json
{
  "candidate_id": "C-0001",
  "problem_binding": "真实固定问题摘要",
  "threat_model_complete": false,
  "attack_or_gap": "可单独核查的模型漏洞或最小反例",
  "affected_obligations": ["O-001"],
  "evidence_refs": [],
  "decision": "NEEDS_REVIEW",
  "claim_status_changed": false
}
```


## 6. 必做的离线自动测试

## 2. 设计裁决与数据流

### 15.1 裁决分层

候选状态可以根据有证据的结构审查转为 `REFUTED/COVERED/RETIRED/CONDITIONAL`；对 `COVERED/REFUTED` 需要定理级原文映射或可复核反例证书。一个候选被否决不代表其父问题或全部同族构造都不可能。

### 15.2 切换协议

完成当前尝试检查点 → 原 `attempt close` 保存历史 → 验证新问题版本和 GOAL 锚点 → 原 `problem import`（若尚未登记）→ 显式 `attempt start` → `run`。所有累计路线消耗依然来自老账本，保留历史输入哈希。

### 15.3 分支搜索和监督联动

监督可以推荐从已否决候选切换，但不能绕过正在进行的固定问题、route pending review、STOP 状态或用户冻结的科研目标。
