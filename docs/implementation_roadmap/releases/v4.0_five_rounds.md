# CryptoResearchController v4.0：五轮实施文档（合集）

此文件合并了单独的 5 份轮次实施文档；每轮仍应单独交给 Codex 执行并验收。

# v4.0 · 开发轮次 R16：密码学科研基准题库与隐藏标准答案

> **执行状态：待开发（计划文件）**。本文是交给 Codex 的实施规格，并非已完成的功能说明。
> **基准：** `Jumpoutbush/CryptoResearchController@67618536ecd172b2fad24843daf291489e226c2e`；执行前以本机较新、已提交的源代码为准。
> **轮次类型：** 软件开发轮次；不得消耗任何个人科研项目的研究预算。

## 1. 本轮唯一目标

先建立一个覆盖查新、反例、安全漏洞、数学障碍、研究偏移、状态恢复的可独立评分任务集，避免“代理自评自己进步”。

**现有基础：** 目前控制器已有 research benchmark 协议与部分离线检查（见 `docs/MATHEMATICAL_DISCOVERY_V3.2.md`）；扩展时先核对现有 `tests/research_benchmark`，不要复制另一份重复基准。

**进入条件：** v3.5 发布验收完成；原始的科研执行、候选和监督都能在模拟环境重放。

## 2. 设计裁决与数据流

### 16.1 30 题起始建议

六类、每类 5 题，逐步补齐**独立金标准**：已知论文定理覆盖、隐藏算术或协议反例、模拟安全漏洞、未闭合数学障碍、跨轮目标跑偏、历史状态恢复。初期应先纳入已有答案的可验证题；真正开放难题只能评分界定能力，不能以“没有解决”作为自动错误。

### 16.2 双层题目文件

代理可见 `task.json`：冻结目标、允许输入、预算、可用工具和预期产物。评价器私有 `oracle.json`：真实答案、攻击见证、判定规则、专家审核与来源；私有目录在代理工作区之外。测试题中的学术引用必须有真实来源或明确标注为合成教学夹具。

## 3. 修改范围（新增文件均为规划路径）

- 新建/扩展 `evaluation/benchmarks/manifest.json`、`evaluation/benchmarks/public/`。
- 隐藏金标准建议存 `state/evaluation/private_oracles/`，不包含在 Codex 监督快照中。
- 新建 `evaluation/validate_cases.py`，与现有 `tests/research_benchmark` 对接。
- 添加 `tests/test_benchmark_dataset.py` 和各类至少一份端到端有效示例。

## 4. Codex 必须完成的实现步骤

1. 先审计当前 benchmark 目录和验证工具，列明可复用、不可重复的样本。
2. 为每题固定 `case_id/version/type/input_sha256/oracle_sha256/evaluator_version`。
3. 设定强制来源：真实既知结果要精确引文；合成反例必须给出可执行谓词与见证；开放问题须标记 `OPEN`。
4. 将 agent-visible 与 oracle-visible 数据分离在权限和路径层，测试代理拿不到金标准文件。必须有真实的操作系统权限隔离/独立沙盒验证；只靠提示词或更换工作目录不能保证隔离。隔离未经验证时标为 `NOT_ISOLATED`，不得计入基准。必须有真实的操作系统权限隔离/独立沙盒验证；只靠提示词或更换工作目录不能保证隔离。隔离未经验证时标为 `NOT_ISOLATED`，不得计入基准。
5. 为论文覆盖、新颖性和安全错误分别设计客观证据检查，而非仅用模型打分。
6. 题目变更需要新版本及审查记录；不能静默改写历史金标准以提高得分。

## 5. 输入、输出与接口约定

参考 schema：

```json
{
  "case_id": "BENCH-LIT-001",
  "version": 1,
  "category": "THEOREM_COVERAGE",
  "public_input_path": "evaluation/benchmarks/public/BENCH-LIT-001/task.json",
  "oracle_path": "state/evaluation/private_oracles/BENCH-LIT-001/oracle.json",
  "source_review_status": "CURATED_OR_SYNTHETIC_EXPLICIT",
  "scoring_rule_version": 1
}
```

真实答案和来源哈希不能使用上述示意值替代。


## 6. 必做的离线自动测试

- 金标准字段不出现在给科研代理的输入快照与提示词中。
- 每类至少一个正例、一个假阳性/假阴性防范测试。
- 已知定理覆盖任务必须具备原文定位或事先经审查的书面推导。
- 开放问题禁止按“是否找出新证明”自动评分。
- 题库修改后能查询完整版本差异与责任人。

## 7. 本轮验收标准

- 首先完成 6 类各至少 1 个真实可评分夹具，再扩展到目标 30 题。
- 至少一项评价器能凭明确反例见证输出确定性判断。
- 隐藏答案隔离测试通过。

## 8. 停止、回滚及禁止事项

若金标准不能独立验证，该题只能设为 `PENDING_CURATION`，不能进入正式质量统计。

## 9. Codex 交付回执

- 填写修改文件列表、设计偏差及理由、`git diff --stat`。
- 提供专项测试与全套回归测试的真实命令、退出码、通过/失败数量。
- 输出一项**独立可复核**的正常路径证据和一项故障注入证据（测试文件/夹具/日志均可）。
- 报告是否改变既有科研项目的 `GOAL.md`、`STATE.json`、预算账本、门禁或任何证明结论；正常答案必须为“均未改变”。
- 使用英文、范围明确的 Git 提交说明；用户未授权时不要推送远端。

# v4.0 · 开发轮次 R17：固定输入、确定性离线科研回放

## 1. 本轮唯一目标

建立不消耗付费模型调用的基准重放能力，对比单代理、控制器、控制器加监督、完整版本四种策略；支持故障注入和历史复现。

**现有基础：** `runner_core.ProjectTransaction`、现有测试假 Codex、`state/routes` 和 discovery 账本已提供可复现记录点；新增回放应只在隔离工作区模拟。

**进入条件：** R16 至少 6 个经过检查的可评分夹具与隔离规则。

## 2. 设计裁决与数据流

### 17.1 四条固定对照

A：单代理模拟；B：基线 v3.2 控制器；C：v3.3 监督启用；D：v3.4+v3.5 完整增强。对照使用相同公开任务、相同预先录制的代理输出或相同受控模型调用限制。模型版本、采样随机性和工具差异不能悄悄改变。

### 17.2 真实可重放性的边界

离线模拟可检验调度、权限、预算、证据回收与评价器，**不能证明真实语言模型能力提高**。真实模型比较必须另外安排统一预算、冻结题目、足够样本并记录误差区间。

## 3. 修改范围（新增文件均为规划路径）

- 新建 `evaluation/replay.py`、`evaluation/fake_codex.py`、`evaluation/isolation.py`。
- 新增 `research.cmd bench replay <case> --variant <A|B|C|D> --offline` 等入口，命令仅在实现后公布。
- 添加 `tests/test_benchmark_replay.py` 和中断/重试夹具。
- 结果写 `state/evaluation/runs/`，不写入个人科研项目。

## 4. Codex 必须完成的实现步骤

1. 每次回放从只读快照复制到临时沙盒，隔离 Git 工作树、环境凭据和隐藏金标准；实际核查操作系统级权限，而不能只依赖提示词。
2. 固定测试种子、输入排序、模型伪响应及文件内容；保存 fixture 的 SHA 和控制器源码提交哈希。
3. 执行流程包括触发、研究回执、证据验收、监督队列、知识图谱更新与候选状态，必要时用假执行器替换 Codex。
4. 输出事件追踪 `events.jsonl`，逐项标注科研调用、监督调用、工具核验与失败。
5. 对中断恢复采用真实日志+检查点，不在回放时修改原有历史科研记录。
6. 不允许回放读取私有 oracle 直到评价阶段，确保分离。

## 5. 输入、输出与接口约定

模拟 CLI：

```powershell
.\research.cmd bench replay BENCH-LIT-001 --variant B --offline
.\research.cmd bench replay BENCH-LIT-001 --variant D --offline
```

结果保留 `controller_commit, fixture_hashes, variant, trace_hash, cost_counts, evaluator_version`。


## 6. 必做的离线自动测试

- 同一版本、种子和输入重复运行的可判定事件轨迹哈希一致。
- 断电/半完成状态只回收当前回放，不影响其他任务。
- A/B/C/D 对照均使用同一 public task 和 oracle 评分规则。
- 实验模拟器没有任何付费请求、无网络下载、没有向本机科研目录写入。
- 科研与监督调用次数分别登记，失败调用计费情况清晰。

## 7. 本轮验收标准

- 可复现一个已知失败的科研漂移测试，以及监督介入后的行为改变。
- 证明的是**控制流程**在测试条件下可靠，不能宣称开放数学任务成功率改善。
- 有结构化轨迹和差异说明。

## 8. 停止、回滚及禁止事项

若运行环境不能完全重现原依赖和固定论文原文版本，报告应给出不可比较原因，而不是把结果纳入总分。

# v4.0 · 开发轮次 R18：科研质量指标、消融对照与独立评分

> **执行状态：待开发（计划文件）**。本文是交给 Codex 的实施规格，并非已完成的功能说明。
> **基准：** `Jumpoutbush/CryptoResearchController@67618536ecd172b2fad24843daf291489e226c2e`；执行前以本机较新、已提交的源代码为准。
> **轮次类型：** 软件开发轮次；不得消耗任何个人科研项目的研究预算。

## 1. 本轮唯一目标

提供可审计的实证指标，证明某项架构升级究竟改善了哪种行为；每个指标给出分母、金标准和置信不确定性。

**现有基础：** 现有 `ROUND_REVIEW` 可区分核心/支持性工作，v3.4 索引能记录主张审查，v4.0 R16—R17 具备题目与离线回放轨迹。

**进入条件：** R16—R17 有经过审核、可重放且独立隔离的任务结果。

## 2. 设计裁决与数据流

### 18.1 指标按真值来源分层

- **确定性：**预算违规数、重放失败数、非法写入成功数、重复事件、原文 SHA 误引、误提升主张状态。
- **基准真值：**隐藏反例命中率、已知覆盖识别率、非事实声称率、错误归责率。
- **专家审查：**复杂安全归约缺口、创新性判断、是否推进核心目标；需双盲或至少独立复核。

### 18.2 统计注意

必须明确成功样本数、总样本数和 95% 区间；样本只有几题时，报告原始计数和个案，不以大幅百分比声称一般化能力。对比 A/B/C/D 时固定同一题目集和工具预算，按任务配对报告差异，不能把不同任务类型的得分直接平均成“科学能力”。

## 3. 修改范围（新增文件均为规划路径）

- 新建 `evaluation/metrics.py`、`evaluation/reporting.py`。
- 新建 `evaluation/scorers/`，按任务类型分别定义硬指标与人工审查输入。
- 添加 `tests/test_metrics.py`、`tests/test_ablation.py`。
- 输出 `reports/evaluation/<run-set>/` 中的 Markdown/JSON 报告。

## 4. Codex 必须完成的实现步骤

1. 为每项指标定义 numerator、denominator、排除条件、数据源与解释范围。
2. 实现对同一题的配对比较（baseline vs enhanced），保存各题结果和版本。
3. 对跨任务模型差异，列出固定模型、推理强度、单题 token 与调用次数（若 CLI 无法获得 token，标为 UNKNOWN，不猜测）。
4. 报告算法支持置信区间，但不能把区间显示精度当成真实性能精度。
5. 加入漏检计数：没有证据支持的监督成功不得记作科学成功。
6. 生成自动报告后仍保留人工审查格；人工标注可核查人员和证据版本。

## 5. 输入、输出与接口约定

对于二项样本结果，报告应使用独立块公式，例如：

\[
\begin{aligned}
s &= \text{通过金标准的题目数},\\
n &= \text{进入统计的有效题目总数},\\
\widehat{p} &= \frac{s}{n},\qquad n>0
\end{aligned}
\]

实际 Python 指标接口应使用英文变量命名与明确定义，不依赖截图识别；数学公式在正式论文输出中再使用严格符号系统。


## 6. 必做的离线自动测试

- 分母为 0 时输出 `UNDEFINED`，而非 0% 或 100%。
- 两个版本同一真实 case 必须按 ID 配对；多次重放不能作为独立题目数量。
- 缺少 oracle 时结果不能进入精确命中率。
- 一个被模型错误认可的候选定理计入错误认可指标，不按文本质量加分。
- 基准题改变时，旧版本报告继续指向旧 oracle SHA。

## 7. 本轮验收标准

- 输出 A/B/C/D 的逐题差异、汇总、成本与不确定性，而非只给一项综合总分。
- 样本过少时保留“结论不足”的明确标识。
- 实验报告能反向追溯原始回放轨迹与金标准。

## 8. 停止、回滚及禁止事项

任何评价模型只能辅助标注，无法独立建立公开数学定理的新颖性与正确性金标准。

## 9. Codex 交付回执

- 填写修改文件列表、设计偏差及理由、`git diff --stat`。
- 提供专项测试与全套回归测试的真实命令、退出码、通过/失败数量。
- 输出一项**独立可复核**的正常路径证据和一项故障注入证据（测试文件/夹具/日志均可）。
- 报告是否改变既有科研项目的 `GOAL.md`、`STATE.json`、预算账本、门禁或任何证明结论；正常答案必须为“均未改变”。
- 使用英文、范围明确的 Git 提交说明；用户未授权时不要推送远端。

# v4.0 · 开发轮次 R19：证据驱动的影子自适应调度策略

> **执行状态：待开发（计划文件）**。本文是交给 Codex 的实施规格，并非已完成的功能说明。
> **基准：** `Jumpoutbush/CryptoResearchController@67618536ecd172b2fad24843daf291489e226c2e`；执行前以本机较新、已提交的源代码为准。
> **轮次类型：** 软件开发轮次；不得消耗任何个人科研项目的研究预算。

## 1. 本轮唯一目标

让控制器基于历史任务评价提出调度策略调整建议，先只在影子模式运行；任何实际影响研究预算或门禁的变动都需用户批准。

**现有基础：** `config/route_policy.json` 和 `config/discovery_defaults.json` 已有预算阈值与有界扩展，`research_focus` 负责核心目标固定；R18 可测评策略表现。

**进入条件：** R18 已具有可信、配对的基准对照结果或明确报告样本不足。

## 2. 设计裁决与数据流

### 19.1 先做影子策略

`SHADOW` 根据既有状态计算“如果改变监督频率、候选筛选比例、检索预算，理论上下一步会怎样”，但不真的改变本轮科研路由和模型。策略输入包括真实核心进展信号、预算消耗、证据覆盖风险、独立审查积压、过去的误监督数。

**硬约束不可学习放宽：**GOAL/腐化门槛/冻结目标、证明义务、独立审查 G8、总预算上限、用户停止状态和科学验证等级。

### 19.2 部署协议

在离线基准存在可复核质量改善证据后，提交 `PolicyProposal`：原参数、拟改值、受影响范围、证据、风险、回滚点。用户批准后只能改变原控制器合法配置字段；同轮不得悄悄新增付费模型请求。

## 3. 修改范围（新增文件均为规划路径）

- 新建 `evaluation/policy_adaptation.py`、`evaluation/policy_registry.py`。
- 新建 `config/evaluation_policy.json`，默认 `mode=SHADOW`、适应参数白名单。
- 添加 `tests/test_shadow_policy.py`、预算上限/STOP/主线绑定测试。
- 在 `research.py` 增加 `bench policy preview/status` 的只读命令。

## 4. Codex 必须完成的实现步骤

1. 只对“监督周期 2/3/4 已验收轮、候选活跃上限 1/2/3”等有界参数做离线比较；预算参数只有在人审批准后才能经原接口修改。
2. 每项建议附至少一个独立真实案例或充分说明样本不足；一旦无法比较，输出 `NO_CHANGE_RECOMMENDED`。
3. 记录 shadow policy 当时本会执行的动作与实际动作，但不伪造因果效果。
4. 策略每版保留输入评价集版本、规则版本与来源哈希；防止使用同一小样本不停优化。
5. 对敏感结论采用人工批准和回滚接口；影子策略只能建议，不能调用 `refocus/route-sync/clear-stop`。
6. 编写复现脚本比对应用前后的原 `route_budget` 行为，确保科研门禁未被弱化。

## 5. 输入、输出与接口约定

影子建议示例：

```json
{
```

## 6. 必做的离线自动测试

- 用一套假数据诱使策略无限追加预算，检查被固定上限拦截。
- 处于 STOP 或活动固定命题中时，策略不能自动开新研究轮。
- 关闭 shadow policy 后控制器行为与旧配置一致。
- 同一评估数据反复重跑不产生重复“有效进展”。
- 参数批准后可无损回滚至原配置及原预算账本。

## 7. 本轮验收标准

- 至少一套影子比较报告说明新策略可能改变哪些触发事件，但项目实际路线和指南未被修改。
- 科学门禁、冻结目标与预算不变量全部保留。
- 新策略没有通过评价前不能自动启用生产模式。

## 8. 停止、回滚及禁止事项

不得以“累计奖励分高”或模型自评高为理由自动更改安全定义。初期避免引入难以审计的黑盒强化学习策略。
