此文件合并了单独的 5 份轮次实施文档；每轮仍应单独交给 Codex 执行并验收。

# v3.4 · 开发轮次 R06：基于现有主张图建立统一证据投影

> **执行状态：待开发（计划文件）**。本文是交给 Codex 的实施规格，并非已完成的功能说明。
> **基准：** `Jumpoutbush/CryptoResearchController@67618536ecd172b2fad24843daf291489e226c2e`；执行前以本机较新、已提交的源代码为准。
> **轮次类型：** 软件开发轮次；不得消耗任何个人科研项目的研究预算。

## 1. 本轮唯一目标

统一引用论文、证明义务、主张、反例、候选和研究轮次的实体身份；先做**派生只读图索引**，不替换现有 `engine/claim_graph.py`。

**现有基础：** `claim_graph.load/status/refresh` 是已存在的主张版本与审查接口；`research/PROOF_OBLIGATIONS.json`、`reports`、`literature` 属于不同资料层。

**进入条件：** v3.3 发布门禁通过，监督报告已有真实引用路径。

## 2. 设计裁决与数据流

### 6.1 最小图模式

节点 `PROJECT, GOAL, PROBLEM_VERSION, OBLIGATION, CLAIM_REVISION, EVIDENCE_FILE, SOURCE_VERSION, RESEARCH_RUN`；边 `REQUIRES, SUPPORTS, REFUTES, DERIVED_FROM, REVIEWED_BY, USES_SOURCE`。每条边存 `provenance_kind`、`source_path`、`source_sha256`、`scope`、`verified_status`。同名主张在两个项目中拥有不同稳定 ID。

### 6.2 权威与派生分离

从旧主张图读取结果时，只能保留其现有 `proof_status`、`novelty_status` 和失效原因；禁止在索引中把模型候选升级成独立审查。历史 Markdown 无结构字段时，最多生成 `UNVERIFIED_TEXT_REFERENCE`，不能构造确定性逻辑依赖边。

## 3. 修改范围（新增文件均为规划路径）

- 新建 `knowledge/schema.py`、`knowledge/build.py`、`knowledge/adapters/claims.py`。
- 新建 `state/knowledge/<project_id>/index.sqlite` 或内容寻址 JSON 索引，明确其为可删重建缓存。
- 新建 `tests/test_knowledge_projection.py`。
- 在 `research.py` 增加只读 `knowledge status <项目>` 和 `knowledge build <项目>`（实现并验证后开放）。

## 4. Codex 必须完成的实现步骤

1. 明确图节点 ID 规则：`project_id:kind:source-id:revision`，绝不只按标题或自然语言字符串合并。
2. 从 `engine/claim_graph.status()` 建主张与其精确问题、义务、依赖边；每条继承权威状态。
3. 从旧路线账本抽取科研轮次和目标锚点，不在索引建立新预算。
4. 使用版本化的 `schema_version=1`；索引内容需包含来源 schema 版本与构建器版本。
5. 构建顺序稳定，重复构建无变化时最终摘要一致，避免过度重建。
6. 将索引写在 `state/knowledge`，不写入用户的 `research/discovery/CLAIM_GRAPH.json`。

## 5. 输入、输出与接口约定

建议公共接口：

```python
build(project) -> BuildReceipt  # 返回输入清单、索引摘要、节点数、边数
explain_claim(project, claim_id, revision=None) -> EvidenceSubgraph
```

输出需携带 `claim_revision`、`proof_status`、`invalidation_reasons` 等来自权威模块的字段。


## 6. 必做的离线自动测试

- 两条同标题却不同前提/项目的主张生成不同节点。
- 没有 claim 图或文献时可构建空图并显示覆盖缺口。
- `claim_graph` 中已有上游依赖失效时，索引展示同样原因。
- 删除 `index.sqlite` 后重建结构和摘要一致。
- 模型未审查主张无法通过索引导出“已证”状态。
- 对一份人工修改的证据文件重新构建，来源哈希改变且影响边被标记待刷新。

## 7. 本轮验收标准

- 有一个在虚拟项目中展示 CLAIM→OBLIGATION→PROBLEM→GOAL 的真实查询。
- 索引完全可重建，项目原始证据哈希在构建前后不变。
- 既有 `claim show/status` 结果不变。

## 8. 停止、回滚及禁止事项

禁止首次升级就引入复杂远端图数据库、Neo4j 服务或自动向量嵌入付费接口。所有图结论必须追溯权威来源。

## 9. Codex 交付回执

- 填写修改文件列表、设计偏差及理由、`git diff --stat`。
- 提供专项测试与全套回归测试的真实命令、退出码、通过/失败数量。
- 输出一项**独立可复核**的正常路径证据和一项故障注入证据（测试文件/夹具/日志均可）。
- 报告是否改变既有科研项目的 `GOAL.md`、`STATE.json`、预算账本、门禁或任何证明结论；正常答案必须为“均未改变”。
- 使用英文、范围明确的 Git 提交说明；用户未授权时不要推送远端。

# v3.4 · 开发轮次 R07：原始论文、定理和引文的版本化溯源

> **执行状态：待开发（计划文件）**。本文是交给 Codex 的实施规格，并非已完成的功能说明。
> **基准：** `Jumpoutbush/CryptoResearchController@67618536ecd172b2fad24843daf291489e226c2e`；执行前以本机较新、已提交的源代码为准。
> **轮次类型：** 软件开发轮次；不得消耗任何个人科研项目的研究预算。

## 1. 本轮唯一目标

为图谱增加原始论文与定理级来源，严格区分摘要检索、全文定位、定理核查和模型推断；避免错误文献覆盖使路线被误杀。

**现有基础：** 现有 `literature/technical_reviews/` 使用六维技术比较，`research_quality.validate_technical_review()` 对全文与哈希有校验，`paper ingest` 保存原始 PDF 摘要。

**进入条件：** R06 图谱节点与边身份稳定且可重建。

## 2. 设计裁决与数据流

### 7.1 来源证据对象

`SOURCE_VERSION` 绑定论文标题、作者、会议/预印本版本、URL、PDF SHA-256、文字提取版本。`THEOREM_SPAN` 必须记录页码/章节/定理标记、文字摘要与对应版本；定位未知为 `LOCATION_UNVERIFIED`，绝不猜测页码。

技术覆盖判断由已有近邻文献审查模板及来源推出。新增图谱只允许把 `UNVERIFIED/RELATED/PARTIAL_OVERLAP/COVERS/CONTRADICTS` 的现有审核结果映射到节点，不允许自己判断“已经覆盖”。

## 3. 修改范围（新增文件均为规划路径）

- 新建 `knowledge/sources.py`、`knowledge/adapters/technical_reviews.py`。
- 增加 `knowledge/source_schema.json` 或等价 Python 数据类。
- 新建 `tests/test_source_provenance.py` 和至少三份虚拟来源文档。
- 扩充 `knowledge explain ...` 输出 `source_file, sha256, location, review_status`。

## 4. Codex 必须完成的实现步骤

1. 复用 `literature/uploads.json`、`pdf_index.json` 和技术审查结果；逐项核对真实结构，不能以猜测字段直接使用。
2. 同一论文不同预印本版本分别建源节点，新增 `SUPERSEDES` 引用但保留旧证据。
3. 将每项“定理级覆盖”边绑定一份已有 `technical_review` 和其全文哈希；无此证据时是候选关系。
4. 设计引文引用串，例如 `project::source_sha::section/page::review_sha`，仅作为数据 ID，不能替代真正原文核对。
5. 原 PDF 缺失、重复上传、提取失败或页码偏移时，输出具体状态和恢复动作。
6. 图谱构建不主动进行网络下载；原文更新只走现有 `paper ingest`/`fetch` 合法接口。

## 5. 输入、输出与接口约定

建议返回结构：

```json
{
  "source_id": "project:sha256:paper",
  "version": "作者原文版本（核查后填写）",
  "source_sha256": "实际哈希",
  "location": "第 x 页／定理编号，待人工核对",
  "review_status": "FULLTEXT_CHECKED 或 LOCATION_UNVERIFIED",
  "technical_review_path": "项目相对路径或 null"
}
```

标签与枚举最终应和已有 `research_quality` 模式保持映射清晰。


## 6. 必做的离线自动测试

- PDF/文字提取文件被替换后，来源校验拒绝旧定理引用。
- 两个版本的同一论文不能因为标题相同被视为内容相同。
- 无全文只有搜索结果摘要时，禁止 `COVERS` 级判定被新图谱主动赋予。
- 含虚假页码、相对上级目录、SHA 不匹配的人工引文记录被拒绝。
- 重建图谱时无任何网络调用、无源码写入。

## 7. 本轮验收标准

- 最少一条技术审查可以从主张边追溯到实际原始 PDF 摘要、论文版本和定理位置。
- 未核查的定位被显式标记且不会进入定理覆盖证明。
- 新增来源索引不改变任何旧技术审查裁决。

## 8. 停止、回滚及禁止事项

无法获得原 PDF 时记录 `MISSING_PRIMARY_SOURCE` 并阻止使用该来源支持决定性否决。

## 9. Codex 交付回执

- 填写修改文件列表、设计偏差及理由、`git diff --stat`。
- 提供专项测试与全套回归测试的真实命令、退出码、通过/失败数量。
- 输出一项**独立可复核**的正常路径证据和一项故障注入证据（测试文件/夹具/日志均可）。
- 报告是否改变既有科研项目的 `GOAL.md`、`STATE.json`、预算账本、门禁或任何证明结论；正常答案必须为“均未改变”。

# v3.4 · 开发轮次 R08：事件溯源、修订链与依赖失效传播

> **执行状态：待开发（计划文件）**。本文是交给 Codex 的实施规格，并非已完成的功能说明。
> **基准：** `Jumpoutbush/CryptoResearchController@67618536ecd172b2fad24843daf291489e226c2e`；执行前以本机较新、已提交的源代码为准。
> **轮次类型：** 软件开发轮次；不得消耗任何个人科研项目的研究预算。

## 1. 本轮唯一目标

让每条图谱关系说明“何时成立、何时失效、为何失效”，并保持既有主张图的独立审查权限不被新索引扩大。

**现有基础：** `engine/claim_graph.import_claim` 已能维护 revision、dependency_pins、history，`status()` 会计算变更、证据缺失与依赖非有效等失效原因。

**进入条件：** R06—R07 已提供来源图与完整的原文定位字段。

## 2. 设计裁决与数据流

### 8.1 权威状态传播

禁止实现第二套“认可主张”的状态机；图谱仅定期读取 `claim_graph.status()`，把 `PENDING_REVALIDATION` 等权威结果映射为带时间戳的投影事件。

新增 `GRAPH_INVALIDATED` 事件时保留：上游变更的具体 `spec_sha256/source_sha256`、影响下游 ID、失效判据、索引版本、时间及操作名。修订后的再次确认必须引用新的真实审核回执，不得把旧审查证明复制过去。

### 8.2 知识回放

支持按一次索引构建之前/之后的版本比较，使监督代理能够回答“为什么这轮后结论不再可用”。事件日志为追加式，并带前一事件摘要，发现历史篡改给出错误而不是自动修复。

## 3. 修改范围（新增文件均为规划路径）

- 新建 `knowledge/events.py`、`knowledge/lineage.py`，增加缓存 schema revision。
- `knowledge explain <项目> --claim <ID>` 增加依赖链和失效因果路径。
- 新建 `tests/test_knowledge_invalidation.py`、三层依赖模拟夹具。

## 4. Codex 必须完成的实现步骤

1. 构造虚拟 A→B→C 主张依赖，A 变更后重新调用原 `claim_graph.refresh/status`，投影 C 的失效原因。
2. 通过规范化输入生成可哈希事件，以真实 source manifest 判断新旧内容而非文件修改时间。
3. 同样的上游变化重新同步只能生成一次失效事件；重复命名相同内容不重新计数。
4. 输入证据恢复后仍需要旧门禁要求的独立审查，不因为索引重建自动升状态。
5. 提供 `knowledge diff` 的纯只读比较输出，说明受影响节点与原因。
6. 模拟写入中断后使用临时索引+原子替换或数据库事务恢复，破损索引可全量重建。

## 5. 输入、输出与接口约定

新接口建议：

```text
knowledge diff <project> --from-index <digestA> --to-index <digestB>
knowledge explain <project> --claim CLAIM-001
```

如果旧索引版本已清理，明确返回 `HISTORY_UNAVAILABLE`，不伪造时间序列。


## 6. 必做的离线自动测试

- 三层依赖正确受 A 的修订影响，且已有 `claim_graph` 状态与索引显示一致。
- 只改文件时间戳不产生虚假证据修订事件。
- 复原文件但无新审查时，不自动把下游结论标为可信。
- 事件日志发生哈希链不一致时给出篡改报告，并允许用权威原始文件重建索引。
- 对重复/损坏 event 的测试保证读取不会递归失控。

## 7. 本轮验收标准

- 查询一条结论可以列出精确的上游失效原因、修订版本和证据路径。
- 科研 `CLAIM_GRAPH.json` 文件在全过程中只由既有模块管理。
- 图谱删掉重建不丢掉权威证据。

## 8. 停止、回滚及禁止事项

不要声称纯哈希链能防止拥有文件系统写权限的攻击者删除所有历史；如需更强防篡改，之后另引入外部时间戳或远端追加日志。

## 9. Codex 交付回执

- 填写修改文件列表、设计偏差及理由、`git diff --stat`。
- 提供专项测试与全套回归测试的真实命令、退出码、通过/失败数量。
- 输出一项**独立可复核**的正常路径证据和一项故障注入证据（测试文件/夹具/日志均可）。
- 报告是否改变既有科研项目的 `GOAL.md`、`STATE.json`、预算账本、门禁或任何证明结论；正常答案必须为“均未改变”。

# v3.4 · 开发轮次 R09：可信分级检索与长期上下文压缩

> **执行状态：待开发（计划文件）**。本文是交给 Codex 的实施规格，并非已完成的功能说明。
> **基准：** `Jumpoutbush/CryptoResearchController@67618536ecd172b2fad24843daf291489e226c2e`；执行前以本机较新、已提交的源代码为准。
> **轮次类型：** 软件开发轮次；不得消耗任何个人科研项目的研究预算。

## 1. 本轮唯一目标

让科研和监督代理只看到最相关、可验证状态明确的证据子图，减少重复补证、错误结论复用与长上下文漂移。

**现有基础：** `runner_core.build_prompt()` 已注入核心目标与最新报告，但长报告会截断；现有 `knowledge`（R06—R08）能提供带身份与哈希的子图。

**进入条件：** R06—R08 的身份、来源和失效链测试通过。

## 2. 设计裁决与数据流

### 9.1 检索排序不等于科学真理

输入为冻结 `goal_anchor`、选中问题/义务 ID、当前任务与预算；优先取该义务的权威主张、必要依赖、反例、被覆盖的近邻文献和未解决缺口。排序只决定读什么，不改变证明等级。

推荐检索顺序：问题的必要依赖与反例 → 明确 CORE/DIRECT_DEPENDENCY 的已验收结果 → 原文定理证据 → 待审候选 → 普通背景。缺少必要证据时输出“缺失清单”，而不是填充虚假摘要。

### 9.2 上下文预算

建议单次核心摘要不超过 32 KiB；超额时按照依赖优先级裁剪，显式保留被截断列表、每份摘要源 SHA 与索引版本。

## 3. 修改范围（新增文件均为规划路径）

- 新建 `knowledge/retrieval.py`、`knowledge/context_builder.py`。
- 增加测试 `tests/test_knowledge_retrieval.py` 与固定排序夹具。
- 对 `runner_core.build_prompt` 增加**可开关**的知识子图上下文装配，不替换已有 GOAL、STATE 或报告契约。
- 监督 snapshot 可复用同一个可信检索器；先作为可选模式。

## 4. Codex 必须完成的实现步骤

1. 精确查询优先支持 `claim_id/problem_id/obligation_id`；自由文本仅辅助召回，不能自动合并不同定理。
2. 每个入选片段输出 `source_file + sha256 + claim_revision + verification_status`。
3. 排除已失效结论作为正面依据；可作为“历史失败路线”引用并明确失效条件。
4. 检索对输入状态和索引版本应确定性可重现；默认不引入外部向量服务。
5. 接入 `build_prompt` 时对照原始版本进行差异回归，保证上游目标/安全边界保持完整。
6. 设计 `knowledge context --task ... --dry-run` 的只读预览，列出选入和舍弃的证据。

## 5. 输入、输出与接口约定

建议的 `EvidenceContext`：

```json
{
  "goal_anchor_id": "真实锚点",
  "target_obligation": "O-001",
  "index_digest": "真实索引摘要",
  "selected": [{"node_id": "...", "evidence_sha256": "...", "trust": "..."}],
  "omitted": [{"node_id": "...", "reason": "budget"}],
  "missing_required": []
}
```


## 6. 必做的离线自动测试

- 固定相同查询和索引，排序与摘要字节级一致。
- 当历史最新报告大量描述无关引理时，核心义务相关反例排在前面。
- 上游失效主张不会被当成当前可用定理提供。
- 超过上下文预算时明确显示遗漏的证据和必要依赖。
- 关闭知识检索时提示词与 v3.3 版本无差异。
- 模型注入语句混在论文中，不被提升为 controller 指令。

## 7. 本轮验收标准

- 可以针对一个真实或模拟的复杂证明义务，输出完整的有来源上下文清单。
- 不自动重新认可审查状态，不改变研究任务及预算。
- 知识检索开关在不安装 SQLite 特性时可正常停用。

## 8. 停止、回滚及禁止事项
